## 2. What Pi 1.5.1 allows, and what reaches the model under the bridge

- `tool_result`: "Fired after a tool executes. Can modify result." (`pi: core/extensions/types.d.ts:1058`). The event
  carries `input`, `content: (TextContent | ImageContent)[]`, `structuredContent?`, `isError` (`:1005-1021`). A handler
  returns `ToolResultEventResult { content?, details?, structuredContent?, isError?, usage? }` (`:1129-1140`): "replacing
  `content` without returning `structuredContent` drops the structured content".
- Runner: each handler's `content` replaces the current one and the next handler sees it (`runner.js:918-924`); a
  handler error is reported as an extension error and the loop goes on (`:942-950`). `_afterToolCall` passes the hook
  result on, after image normalisation (`agent-session.js:403-436`); `finalizeExecutedToolCall` applies
  `afterResult.content` (`core/agent-loop.js:607-640`, `:622`), then `createToolResultMessage` builds the `toolResult`
  message from it (`:662-676`). So the text a `tool_result` handler appends is in Pi's `toolResult` message.
- A blocked call is "immediate" and skips `afterToolCall` (`core/agent-loop.js:392-398`, `:427-437`): no reminder on a
  blocked call (R-047's refusal included).
- `bash` and `read` declare an `outputSchema` (`pi: core/tools/bash.js:194`, `read.js:184`); `edit` and `write` do not
  (grep of `core/tools/*.js`). HEAD's vision reminder on a Bash result drops bash's `structuredContent` (`runner.js:920-922`).
- Bridge: "Pi runs the tool itself, so its own tool events and hooks fire. … The result goes back to the waiting
  handler" (bridge-ev:115-118); "Tool results go to the blocked handler: `pending.resolve(result)`" (bridge-ev:51); on
  a rebuild "Tool results are grouped right after their `tool_use`" (bridge-ev:57) and `cc-session-io` writes
  `tool_result` blocks in their own record (bridge-ev:400, :413). E-1's consequence: "only tool results have another
  role" (`plan.md:1616-1617`). So the appended text reaches Claude Code as part of the MCP tool result, not as a `user`
  message; that the resolved result is the post-hook `toolResult` content is read from Pi's order above, not from a
  bridge line (Unverified 1).
- Argument mapping: "`file_path→path` and `old_string→oldText` renames" (bridge-ev:135), so Pi's `edit`/`write` input
  holds `path` (`pi: core/tools/edit.d.ts:6`, `write.d.ts:5`), which `toolPath` reads (`:359-361`).
