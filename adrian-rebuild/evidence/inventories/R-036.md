  - The timer `setInterval(checkStall, 3_000)` (`wrapper.ts:365`) starts after the engine's spawn (`:259-264`) and
    the "worker started" line (`:278`), and is cleared at the engine's end (`:380`). No stall check runs while the
    job waits in the start queue (`:137-155`) or during setup and `--prepare` (`:160-163`). No knob sets the 3 s.
  - `checkStall` (`:350-364`) does nothing while an observation runs, after an exhaustion or without an engine pid;
    when `seen.activity !== "tool"` it clears the uncertainty note and returns (`:354-357`). `activity` is `tool`
    from a `tool_execution_start` until the next activity event (`tool_execution_end` → `wait`,
    `src/runtime/stream.ts:42-47`; `recordEvents`, `wrapper.ts:510-528`).
- What it samples:
  - `observeStall(enginePid)` (`wrapper.ts:305-349`) first reads the engine's `/proc/<pid>/stat`
    (`platform.processInfo`): present, ppid and pgid equal to the wrapper's pid, else the note "detached engine
    ownership unavailable" (`:306-312`).
  - Then `observeToolStall(stallWatch, engine, key)` with the key `${tools}:${seen.tool}:${seen.progress}` (`:313`):
    the tool count, the last tool with its detail (80 characters, `stream.ts:102-113`), and `seen.progress`, +1 per
    stderr chunk (`wrapper.ts:268-271`) and per non-JSON stdout line (`:535-537`). This key is today's "tool
    progress"; a change restarts the watch (`stalled-tool.ts:87-93`).
  - `sampleTree` (`stalled-tool.ts:23-62`): one `ps -Ao pid=,ppid=,pgid=,time=,stat=` (`platform.processTable`,

    earlier tool, the wrapper itself.

## 7. Migration surface

- Record (D-079: a record refuses an unknown field; a new field is optional for older records, `plan.md:1272-1273`):
  - `advisory` is required and strict (§3): a source as a new key needs an optional read or a value for older
    records. Running records meet no new code at a deployment (`plan.md:1833-1834`); terminal records can keep an
    advisory (§3); the migration writes `{ text, at }` (`migration.ts:537`); the hook skips migrated records
    (`hook/wake.ts:645`).
  - `scope` has five strict keys (`record.ts:887-897`), written at the handshake and at the end; a peak as a sixth
    key needs an optional read, or the peak is a new optional top-level field (`queueWait`'s pattern, `:906-907`).
  - The stored `failure.kind` of older `stall` records stays; a new detail text must still give `stall`
    (`record.ts:735`) or set the kind where it is detected (R-029).
- Receipt files in a job folder: `notify/claims/<slot>`, `notify/delivered/<slot>` (`_advisory.<session>`,
  `_advisory._fallback`, and `_uncertainty.*` from before R-005), `notify/unconfirmed/_advisory`,
  `notify/herdr/<slot>`, `notify/seat/_advisory.<at>`. A finished job's advisory receipts matter only by their family
  (`completionSlots`, `wake-delivery.ts:333-335`).
- Group cabinet: the mirrored `<member>-advisory.json` files (`group-events.ts:107-125`) and their text filter.
- `limits.json`: the key `toolStall` (`limits.ts:12`) and its meaning; R-062 later moves owner settings.
- Rollback: after a revert, a record with a new field is `BAD_DATA`, as R-035's `queueWait` is
  (`R-035-start-queue-thresholds/outcome.md:289-290`); the snapshot of step 0.1 is the rollback of a format change.
