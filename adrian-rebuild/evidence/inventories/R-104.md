# Inventory for R-104 (2026-11-26, at `c3bbc5c`)

A read-only subagent inventory (it wrote only this file). Every `path:line` is at HEAD `c3bbc5c`; the tree was clean.
Commands were run from the repository root; their output is quoted where a claim rests on it.

In short, at HEAD: the daily prune moves an unregistered folder of the worktree root into the archive only when it
holds no `.git`; one with a `.git` that is clean, or that Git cannot read, is still deleted. Prune waits up to 60 s for
each folder's lock while it holds the jobs lock; retire takes the same lock with one attempt. A writer that takes a
job's lock after a retire makes the job folder again (the lock module's `mkdir`), and the next daily prune's move of
that empty folder runs into the retired job's folder in the archive and fails the whole prune, every minute, until
the UTC month changes. A start-queue entry is live on a live pid and a `running` record at any path.

## 1. The daily prune at HEAD

Entry: `pruneFinishedWorktrees(root)` (`src/runtime/pruning.ts:105-114`) runs `archiveUnstarted` first (`:106`,

the sweep (`src/runtime/sweeping.ts:301`; scan `test/structure.test.ts:1661-1670`).

The worktree root of a repository is `<dirname(repo)>/.<basename(repo)>-limen-worktrees` (`pruning.ts:534-536`). The
candidates (`removalCandidates`, `:550-571`): each worktree Git lists that `removable` takes (not the primary checkout,
inside the root, not a dot entry, not Git-locked; `:542-545`) is `true`; every other name of the root that does not

(`worktreeClaims`, `:600-618`) and the unlanded work (`:524-532`), runs `prunePass` (`:445-478`) deepest first
(`:451`), and runs `git worktree prune` (`:418`); after the lock `emptyTrash` deletes every `.pruned-*` name
(`:421`, `:642-652`).

Before any move, `heldCandidates` (`:501-518`) marks a candidate held when a finished job's unlanded work names it,
when `git status` lists a change (`worktreeChanges`, `src/project/git.ts:319-332`), or when a nested commit is missing
from the project (`unsavedNested`, `pruning.ts:84-89`). `worktreeChanges` returns `undefined` when there is no `.git`
(`git.ts:320-322`) or when Git says "not a git repository" (`:327-329`), and throws `GIT_FAILED` otherwise
(`:330-331`).

## 3. The empty `.limen/jobs/<id>/` after a retire

Which code makes it. The writers of a record check that the folder exists, then take its lock:
`transition` (`src/job/record.ts:655-660`: `existsSync(jobDir)`, then `withLock({ folder: jobDir })`), `writeMarker`
(`:696-700`), `writeAnyState` (`:821-828`), and `limen stop`'s operation lock `{ folder: jobDir }`
(`src/job/stopping.ts:58`, taken at `src/operation.ts:115`). `acquire`'s `mkdir` (`lock.ts:216`) makes the folder again
when a retire renamed it between the check and the lock; the writer then finds no record and returns or refuses, and
its release removes only `.lock` (`lock.ts:339`), so the folder stays, empty. The code says so itself: `lock.ts:132-133`
("Taking the lock makes the folder when it is missing"), `src/runtime/start-queue.ts:274-276` and `:371-372`.

Why it fails the daily prune. `jobFolders` lists it (`record.ts:392-433`); it has no record, so `everRan` is false
(`src/job/job.ts:34`) and `jobKeeps(jobDir, undefined)` keeps it only for an open group (`pruning.ts:122-131`;
`startingJob(undefined)` is false, `src/runtime/reap.ts:97-99`). It joins `unstarted` (`pruning.ts:287-289`). Under the
jobs lock `archiveFolder(root, id, undefined)` takes the month of the move (`pruning.ts:360-364`: `record?.startedAt ??
new Date().toISOString()`; `archiveMonth` is `.limen/archive/<at.slice(0, 7)>`, `record.ts:440-442`). Retire put the
job at `archiveMonth(root, <marker at>)` (`retiring.ts:83`). When the marker's UTC month is the current one, the target
`<month>/<id>/` is the retired job's folder, which holds its files, so `atomicRename` (`src/atomic-write.ts:92-98`,
`rename`) fails. That plain `Error` becomes `STEP_FAILED`, exit 4 (`operation.ts:185-192`).

Why "until the month changes". The folder has no record, so its target month is the month of each attempt; once the
UTC month differs from the marker's, `<new month>/<id>/` is free and the move goes. The id is then in two months; the
readers skip the copy that never ran (`job.ts:31-34`; `src/job/statistics.ts:160`; `src/integrations/github-review.ts:104`).
No collision happens when the marker's month is earlier than the prune's.

While it fails: no stamp, so the daily steps run every minute (`sweeping.ts:316-331`, `:340-347`); the loop of
`moveUnstarted` stops at the throw, so later folders with no record and the whole worktree pass
(`pruning.ts:106-112`) wait too; retire and the tab close still run (`sweeping.ts:316-322`); `limen status` shows
`Sweep not working` while the service's last run failed (`docs/seat/README.md:45`).

## 4. The start queue's liveness

The entry: the wrapper writes `{ id, jobDir, label, priority, queuedAt, pid }` (`start-queue.ts:51-58`, `:245-252`,
`:484-489`) into `<seat>/.limen/start-queue/entries/<id>.json` (`:72-73`). `jobDir` is the wrapper's `LIMEN_JOB_DIR`
(`src/runtime/wrapper.ts:48`), which spawn and continue set to `<root>/.limen/jobs/<id>` (`spawning.ts:316`, `:452`,
`:694`; `continuation.ts:331`, `:605`).

What makes it live today: `readEntries` (`start-queue.ts:565-591`), line `:584`: a parsed entry (`:619-638`) whose
`platform.processAlive(entry.pid)` holds and whose `entryState(entry.jobDir)` is `running` (`:645-653`; a record that
does not read counts as dead). Nothing ties `jobDir` to a registered project, `id` to `basename(jobDir)`, or `pid` to
the record's `identity`, which the handshake writes (`wrapper.ts:139-143`).

One definition already (T-25): `readEntries` serves all three readers.
- `liveEntries` (`:594-600`) for the waiting wrapper's `decide` (`:491`, the jobs ahead; `:519`, the head check under
  the queue lock), which removes dead entries;
- `queueEntries` (`:603-605`) for `limen seat queue` (`src/runtime/queue-report.ts:32`), read only (T-04);
- `removeDeadEntries` (`:612-618`) for the sweep, once per run, with a strict listing (`sweeping.ts:180-187`).

`git grep -n 'waitForStart\|queueEntries\|removeDeadEntries\|liveEntries' -- src hook test` finds no other reader
(only `start-queue.ts`, `queue-report.ts`, `sweeping.ts`, `wrapper.ts` and `test/runtime/start-queue.test.ts`).

Where the new rule goes: the condition at `start-queue.ts:584`. The registry is `registeredProjects()`
(`src/project/seat.ts:12-16`), a lockless read of `<seat>/.limen/projects`; `limen init` writes it (`src/project/setup.ts:90-91`,
`registerProject`, `seat.ts:34-37`, `resolve(root)`), so does the wake hook (`hook/wake.ts:912`), and the sweep drops
roots that are gone (`sweeping.ts:166-168`). Spawn's root (`limenRoot`, `git.ts:32-53`) and init's root (`setup.ts:21`,
`:39`) come from the same functions (`repoRoot`, `workspaceRoot`).

A consequence to settle: the head check (`:519`, `(await liveEntries())[0]?.id !== entry.id`) needs the wrapper's own
entry to be live, so with the rule as it stands a queued job of a project the seat does not register would never
start and would end `failed`, kind `queue`, at `failAfter` (`:343-345`). The plant registers its project through a real
`limen init` (`test/plant.ts:428-431`), but the unit fixtures of `test/runtime/start-queue.test.ts` plant jobs at
`<home>/repo/.limen/jobs/<id>` with no `projects` file (`seat`, `:50-60`; `queuedJob`, `:75-85`; `threeEntries`,
`:467-478`).

## 9. Open design questions

1. An unregistered folder that Git does read and that is dirty (technical, category A of D-054 (2): settled by the
   documents). Options: (a) only the branch that deletes today becomes a move: the held checks still come first, so a
   dirty clone stays with its `kept` line and a `HEAD` with no commit still fails `GIT_FAILED`; (b) every unregistered
   folder moves with no Git read, except one a job keeps, one a finished job's unlanded work names, and one with a
   registered worktree below; (c) only a `.git` Git cannot read moves (Q-58's option 2, rejected). Recommendation (a):
   D-107 (4)'s purpose is "so nothing Git does not hold elsewhere is deleted", and a kept folder is not deleted; it keeps
   A-001's rule "No removal takes a worktree that `git status` shows dirty, whatever job names it" (`pruning.ts:5-6`,
   `docs/jobs.md:139`) unchanged.
2. The reason of the moved folder (technical, category A). Options: (a) one reason for every unregistered folder,
   `the directory is not a registered Git worktree` (today's deletion reason, `pruning.ts:474`); (b) two reasons, with
   and without a `.git`. Recommendation (a): one thing, one word (T-18), and the line already says where it went.
3. The worktree lock that prune waits for under the jobs lock (`pruning.ts:336`) (technical, category A). It is a
   folder's lock too (`publication.ts:21-23`). Options: (a) one attempt as well; a held lock leaves the publications for
   the next daily run with a line; (b) keep the wait, since publication holds it for one rename (`publication.ts:121`).
   Recommendation (a): R-101 Open point 6's reason, "one rule for every move under the jobs lock", and retire's
   header (`retiring.ts:6-8`). Not (c), taking it before the jobs lock: spawn takes the jobs lock first and the worktree
   lock inside (see Unverified), so the reversed order could make both wait their 60 s.
4. Prune's held folders in its result and its line (technical, category A). Options: (a) `PruneResult` gains `held`,
   and one line function serves both steps (`heldLine` today names retire only, `retiring.ts:48-50`; T-25 (2) moves it
   to the module that owns the concept); (b) a second line function in `pruning.ts`. Recommendation (a), the words as
   `kept job <id> for the next daily prune: another process holds its lock`, beside retire's.
5. The empty folder whose `<month>/<id>` is taken (technical, category A for option (a); option (b) would be a plan
   question for Adrian). Options: (a) on a taken target, a folder with no record moves to
   `.limen/archive/unregistered/<id>-<time>/`, the archive folder "which holds no job" (`docs/jobs.md:149`), so
   nothing is deleted, no reader changes, and a non-empty folder with no record is covered too; (b) a folder with no
   entry at all is removed with one `rmdir` (it fails on any entry, so nothing is lost), which departs from D-097 (4)
   (d)'s "move"; (c) the writers stop making a missing job folder (a lock mode that refuses a missing `{ folder }`),
   which changes R-019's module and every writer and leaves folders already made. Recommendation (a), with the test of
   section 5, item 6; (c) can follow later if such folders keep appearing.
6. What "one of the project's jobs" means (technical, category A for (a) against (c); (b) is a question for Adrian).
   Options: (a) `jobDir` is `<root>/.limen/jobs/<entry.id>` for a root of `registeredProjects()`, compared as real
   paths as prune's `resolved` does (`pruning.ts:654-659`); (b) (a), and the entry's `pid` is the record's
   `identity.pid` with its `born`; (c) the path's shape alone, with no registry. Recommendation (a): D-107 (5) says "one
   of the project's jobs", and Q-59 "against the project's jobs"; (b) goes past the note, while the agents' account can
   write a record anyway (Q-59's option 2 reasoning).
7. A queued job of an unregistered project (technical, category A). Options: (a) the head check (`:519`) and the count
   of jobs ahead (`:491`) judge only the other entries by the rule, so the wrapper's own entry never blocks itself; (b)
   one rule for the own entry too, so such a job waits until `failAfter`; (c) its wait ends at once with a typed
   reason that names `limen init`. Recommendation (a): Q-59's harm is holding other jobs' starts, and (a) keeps one
   definition for every other entry.
