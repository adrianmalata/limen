## 2. What a `main` watcher needs, and what it can reuse

- Its own copy (D-110 "keeps its own clone"): a bare repository in the service's state folder (`StateDirectory=`,
  mode 0700, as `seat/units.ts:50-51`), owned by a non-agents account. A bare repository has no working tree, so no
  checkout, filter or hook of the fetched content runs. A clone made with git's default fetch refspec is not usable as
  is: that refspec forces updates (see Unverified 1), and `--mirror` likewise; the watcher passes its own refspec or
  none.
- Fetch with no forced update every minute: a timer like the alerts' (`seat/units.ts:61-77`, `OnUnitActiveSec=1min`,
  `AccuracySec=1s`). No `+` refspec, no `--force`, no `--prune`, so the held ref never moves backwards and is never
  removed by a fetch. A test can assert the argv of every git call (section 4).
- Three cases to tell apart, by exit codes rather than git's text (T-27 data through validators; T-12 declared tools):
  - remote `main` absent: `git ls-remote --exit-code <address> refs/heads/main` (exit 2 for no matching ref, see
    Unverified 2) → event "deleted", the held ref stays;
  - remote `main` present and not a descendant of the held tip: fetch the object with no ref written (the
    `--no-write-fetch-head` precedent above), then `merge-base --is-ancestor <held> <remote>` exit 1 → event
    "forced"; exit 0 → move the held ref by a checked update (old value given), no event;
  - the remote cannot be reached (network, DNS, refused key, missing repository, timeout): any other failure of the
    network call → no event, the run is class 3 or 4 by T-02, the journal names it.
  The plain alternative, `git fetch <address> refs/heads/main:<held ref>` and its exit 1 with a "rejected" line for a
  non-fast-forward or exit 128 with "couldn't find remote ref" for a deletion, shares exit 128 with network failures,
  so it needs git's English text (Unverified 1).
- Which failures alert and which only log (T-01, T-02): forced and deleted ring at once, once per held tip; an
  unreachable remote logs each run and, by T-02, rings "only after several in a row" (precedents: 3 runs,
  `src/job/record.ts:843-844`; 15 minutes, D-100 `plan.md:1313-1320`); a local failure (no clone folder, git or ssh
  missing, credential missing) is class 4, which T-02 says rings at once, but a broken watcher may not be able to send,
  so `limen status` is the fallback, as for the alerts (`src/project/summary.ts:194-215`).
- Keeping history (D-110 "keeping the history it held"; T-28 (3) "a test that nothing is lost"): after a forced update
  the old tip must stay referenced in the clone (a kept ref), so git never collects it.
- The alert line: D-084's shape is `<project base name> <event> <subject>`, ≤ 100 characters, no path, label or job
  text (`plan.md:1062-1065`); `alertLine` (`seat/alerts.ts:461-472`) already builds `<name> <event> <id>` with the cut,
  so a `main` event with the held commit as the third field fits it.
- Dedup: the alerts' key scheme (`<project path>/<job id>/<kind>`, `seat/alerts.ts:450`) extends to
  `<project>/main/<held tip>/<kind>`, so a second forced update later (another held tip) rings again and the same
  state never rings twice. A key is recorded only after a 2xx (`:214-218`).
- The project list and the address of each repository: the alerts read the agents' registry (`seat/registries.ts:44-52`)
  through ACLs the install grants (`seat/alerts.ts:617-674`). Two facts weigh against taking the watch list or the
  remote address from the agents' side at each run: the registry is a file in the agents' home that `limen init`
  rewrites and an agent can edit (`seat/registries.ts:39-41`; R-033 `outcome.md:278-280`), and A-006's Scenario names
  the agents' power to "overwrite it through the shared hooks directory or repository config" (`audit.md:548`), where
  `origin`'s URL lives. A watcher that read them could be redirected or told to skip a project. The registry still
  serves as a cross-check (a registered project with no watch entry) and as the source of the base name for D-084's
  line.
- Network: B2c's allow-list is per the agents' UID (`gate-2-decisions.md:111-113`, "nftables per UID";
  R-056 "Egress allow-list templates for the
  agents' account", `plan.md:1849`), so it does not restrict a watcher on another account; whether the seat reaches
  GitHub's SSH service is a seat fact (Unverified 9).
- IPv4 first: a watcher that sends from the alerts' unit inherits R-109's setting; one that sends from its own unit
  needs the same `NODE_OPTIONS` setting for D-108's reason. R-106 and R-109 both edit `seat/units.ts`.

## 3. Credentials (by mechanism)

- One read-only deploy key per repository (D-110; step 4.10, Adrian's: "a read-only deploy key whose private half only
  the watcher's account can read", `plan.md:2492-2493`).
- Delivery as for the topic (D-085): the private half sits in a root-owned 0600 file outside any home, and the unit
  hands it to the service with `LoadCredential=`, so it appears only in the service's credentials folder while the
  service runs (`seat/units.ts:49` is the pattern; `seat/alerts.ts:293-323` reads `$CREDENTIALS_DIRECTORY`). The
  install checks each such file as it checks the topic file: regular file, not a link, root's, mode 0600
  (`seat/alerts.ts:586-608`).
- Git gets the key through an ssh command set in git's environment for each network call (`GIT_SSH_COMMAND`, or
  `core.sshCommand` in the clone's own config), naming the key from the credentials folder, using only that key, no
  agent and no user configuration, a pinned known-hosts file that root owns, no prompt, and a connection timeout.
  The credentials folder's path is known only at run time, so the environment form fits better than a stored config.
- The repository's SSH address and the known-hosts lines are data the agents must not change: root-owned files beside
  the key (also loadable as credentials), not `origin` of the agents' checkout (section 2).
- What keeps the agents' account out: the key file is root's 0600; the credentials folder is the service account's;
  the clone is in a 0700 state folder of another UID; `ProtectSystem=strict` leaves only the state folder writable
  (`seat/units.ts:53-56`). Seat check (4.10): as the agents' account, a read of the key file, of the credentials
  folder and of the clone is refused.
- The seat's fine-grained token has Contents read and write only (D-012, `plan.md:313-314`); whether that permission
  can remove a deploy key or change the default branch is a GitHub fact this repository does not settle (Unverified 8).

Q1. Which account runs the watcher. Taste/plan question for Adrian (security, D-054 (2) `plan.md:754`).

Q4. What the watcher does after a forced update. Taste/plan question for Adrian (security behaviour).
- (a) Freeze: the held ref stays at the old tip; later fast-forwards of the new `main` never advance it, and a second
  forced update is not seen as new.
- (b) Keep and follow: the old tip goes to a kept ref (with its time), the held ref moves to the new tip by a checked
  update, one alert; later forced updates ring again.
- (c) Freeze and fail every run until root acknowledges with a command.
- Recommendation: (b): D-110's "keeping the history it held" holds by the kept ref, the watch keeps working, and T-28
  (3) ("running them again and a test that nothing is lost") is testable. After a deletion the held ref stays; a
  re-created `main` is compared with it.

Q5. How the three cases are detected. Technical (category A, D-054 (2) (b)).
- (a) Plain `git fetch` with a refspec without `+`, classified by exit code and git's English stderr (Unverified 1).
- (b) `git ls-remote --exit-code` (found, missing, failure by exit code), then a fetch of the object with no ref
  written and `merge-base --is-ancestor` (exit 0 or 1, `src/project/git.ts:484-491`); the held ref moves only by a
  checked `update-ref`.
- (c) `git fetch --porcelain`: a newer git than the declared ≥ 2.36 (`plan.md:1581`; Unverified 4).
- Recommendation: (b): decisions by exit codes only, git ≥ 2.36 suffices, and no fetch updates the held ref by force,

- (c) Never: only the journal and the service's failed state in `limen status`.
- Recommendation: (b): an outage loses no history (the clone keeps the held tip and the next good run compares with
