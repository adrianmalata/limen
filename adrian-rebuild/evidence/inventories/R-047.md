## 3. What Pi 1.5.1 does with a blocked call

- Types: "Fired before a tool executes. Can block." (`pi: core/extensions/types.d.ts:999`); `input` is mutable
  (`:1001-1002`); `BashToolCallEvent { toolName: "bash"; input: BashToolInput }` (`:962-965`), `command` and an optional
  `timeout` (`pi: core/tools/bash.d.ts:7-8`). `ToolCallEventResult { block?, reason?, terminate? }` (`:1109-1118`):
  terminate is a "Hint that the agent should stop after the current tool batch … only when every finalized tool result
  in the batch sets this to true".
- Runner: `emitToolCall` returns the first result with `block` and has no try/catch (`pi: core/extensions/runner.js:965-979`);
  `_beforeToolCall` rethrows a handler's error (`pi: core/agent-session.js:381-401`).
- Loop: `if (beforeResult?.block) { const result = createErrorToolResult(beforeResult.reason || "Tool execution was
  blocked"); … return { kind: "immediate", result, isError: true } }` (`core/agent-loop.js:513-523`); an immediate result
  skips execution and `afterToolCall` (`:392-398` sequential, `:427-437` parallel); the message is a `toolResult` with
  `content: [{ type: "text", text: reason }]` and `isError: true` (`:646-651`, `:662-676`). With `terminate`, Pi makes no
  further model call in that run (`:172`: `hasMoreToolCalls = !executedToolBatch.terminate`).
- Bridge: the `tool_use` is mirrored into Pi under the Pi tool name, "Pi runs the tool itself, so its own tool events
  and hooks fire", "The result goes back to the waiting handler" (bridge-ev:115-118); "Pi's `tool_call` event sees only
  Pi tool names" (bridge-ev:124). So the reason is the tool result Claude Code's call receives; how Pi's `isError` maps
  into the MCP result is not in bridge-ev (Unverified 1).
