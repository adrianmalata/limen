### 1.1 T-04 (`adrian-rebuild/taste.md:692-709`, in full)

```
### T-04 Read commands never write and never wait
- Rule: Read commands (`status`, `show`, `seat queue`, `stats`, `show --result`, `github show`, `handoff show`; names per T-18)
  never write and never wait. They compute a dead job's state and show it without writing it, e.g. "wrapper dead since
  …; limen-sweep will finalize". The housekeeping before every `limen` call goes. Only `limen-sweep` (A-024) and
  explicit state-changing commands, a manual `limen sweep` included, clean up and finalize.
- Why: the author's read commands reap jobs and can wait 10 s (AU-205); the owner channel and the bell read records
  read-only; a read must be predictable.
- Check: a test asserts that every read command leaves `.limen/` byte-identical and returns without waiting; a test
  runs them on a read-only copy of `.limen/`; the command registry marks each command read or change, and read
  commands do not import the state-transition functions.
- Source: interview round 1, AU-205; departs from the author. 2026-11-23 (`plan.md` D-096 (2), Q-50): `diff` leaves the
  list; `limen diff` and `limen open` are change commands, since each opens a Herdr tab and records its place so that
  Limen can close it (R-103).
  2026-11-25 (`plan.md` D-107 (3), Q-57): "never wait" means no wait without a bound; a read may take a bounded
  reading of an outside system, each bound named here: `limen status`'s Herdr and systemd probes (2–5 s each, among
  them two 3 s probes of user units, R-032) and `limen seat queue`'s 2 s sample of the machine; the read test keeps
  these as its exceptions.
```

### 1.2 T-26 (`adrian-rebuild/taste.md:1236-1254`, in full)

```
### T-26 Commands are thin adapters; logic lives in domain modules
- Rule: Commands are thin adapters; the logic lives in domain modules as typed functions; within a process no command
  calls another, neither through argv nor through an import. (1) A registry command (T-19): parse with the shared
  parser, call a domain operation, pass the result to the shared wrapper, which turns a typed result or error (T-01,
  T-03) into the exit code, the text and the final JSON line (T-02); `next` is a field of the domain error. (2) The
  operations live in the existing domain modules: `src/job/` (spawn, continue, land, abandon, stop), `src/spec/`
  (A-048: tickets, the board, `spec fix`), and the seat module (reaper, resume, prune, retire, queue); `group land`,
  `resume --quota` and `seat sweep` call the same operations. (3) Dependencies point one way: commands → domain; the
  domain imports nothing from `src/commands`, and no command imports another. (4) At a process boundary (Pi hooks,
  systemd timers calling `limen` by an absolute path, A-025) only the final JSON line is read, through one client
  function, never the text meant for a person. (5) Operations are tested directly; commands by golden tests through
  the registry and the wrapper.
- Why: the author's commands call each other by building argv and reading the last stdout line, so `src/commands` is
  also a library (keeper imports land and spawn, land imports prune) (AU-217).
- Check: an import scan: a file in `src/commands` imports nothing from `src/commands` (except the registry's types),
  and domain modules import nothing from `src/commands` or `bin/`; a scan finds no launch of Limen's own CLI (spawn or
  exec of `limen`) in `src/`; hooks call the CLI only through the client function that reads the final JSON line (a
  test with output that has text before the JSON line).
- Source: interview round 7, AU-217; departs from the author.
```

## 6. A design for the transitive-closure scan

Facts it rests on:
- Relative imports in `src/` all end in `.ts"`: `git grep -n -e 'from "\.' --and --not -e '\.ts";$' -- src` → nothing.
  Example: `src/commands/show.ts:1` `import { jobDetail } from "../job/detail.ts";`. `tsconfig.json`:
  `"module": "nodenext"`, `"moduleResolution": "nodenext"`, `"allowImportingTsExtensions": true`,
  `"verbatimModuleSyntax": true`. So `importedFile` (`test/structure.test.ts:1399-1402`) resolves every one; no
  extension or `index` lookup is needed.
- `src/` imports nothing but `node:` modules and relative paths: `git grep -n -e 'from "' --and --not -e 'from "\.'
  --and --not -e 'from "node:' -- src` → one string inside `src/picture/picture-model.ts:863`, no import. No relative
  import leaves `src/` (`git grep -n -e 'from "\.\./\.\./' -e 'from "\.\./hook' … -- src` → nothing).
- No dynamic import in `src/` or `hook/`: the test at `test/structure.test.ts:83-96` (gate 2 §7 D3; "A job's finalize
  path can start a new `bin/limen` … `bin/limen` imports `src/main.ts` dynamically before any job code runs, and is
  outside the scan"). `git grep -nE 'import\(' -- src` → nothing.
- Re-exports and namespace imports in `src/`: `src/platform/platform.ts:202` `export { BOOT_ID } from "./linux.ts";`;
  namespace imports only of `node:fs` (`src/project/seat.ts:1`, `src/runtime/sweeping.ts:14`); no `export *`.
- Cycles exist: `finalize.ts:21` → `group-cabinet.ts:11` → `reap.ts:12` → `finalize.ts`; `record.ts:39` → `job.ts:5`
  → `series.ts:6` → `record.ts`.
- T-12 is about runtime dependencies (`taste.md:841-850`; "the empty-`dependencies` test stays",
  `test/structure.test.ts:25-31`). `typescript` is a devDependency (`package.json`), already used by
  `test/imports.ts:3` and `test/structure.test.ts:8`; R-025's scans go "through the TypeScript syntax tree"
  (`plan.md:3698-3699`). Reusing `importsOf` adds no dependency.

Shape (a pure function, so a fixture test can feed it files):
1. Inputs: the read commands with their handler files (as `:1102-1111` builds them), and the text of every git-known
   file of `src/` (`knownSources(["src"])`, `:98-105`, the walk of D-075).
2. For each read command, walk from its handler file with a queue and a `seen` set (cycles end there).
3. For each file, take `importsOf(file, text)`. Skip `typeOnly`. A `module` that is `undefined` (a computed
   `import(…)`) is a finding. Resolve with `importedFile`; skip `undefined` (`node:`). Every name in
   `STATE_TRANSITIONS` is a finding `<command>: <file> imports <name>`. A `namespace` or `star` import of a `src/` file
   is a finding, since its names are hidden. Queue every resolved `src/` file not yet seen, `import { type X }`
   included (only `import type` is erased by name; see Unverified).
4. A file that is not a known file is a finding (an import of an untracked or missing file).
5. Compare the findings with the ratchet both ways (section 7). Name the chain only in the assertion message, so the
   ratchet does not change when an unrelated import moves.

Fixture test (one mechanism each, T-29 (3)): two levels deep; a cycle; `export { … } from`; `import type` skipped;
`import { type X, f }` followed; a namespace import of a `src/` file found; a `node:` import skipped. Where it lives
(`test/imports.ts` beside `importsOf`, or `test/structure.test.ts`) is a technical choice.

Note for the ticket's Why: `src/main.ts:5` imports `REGISTRY`, so a read command's process loads every command's
module. The scan proves that the read path's own module graph imports no transition, not that the process holds no
transition code.
