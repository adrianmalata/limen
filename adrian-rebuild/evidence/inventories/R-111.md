# Inventory for R-111 (2026-11-26, at `aae86b7`)

Short version. Pi 1.5.1 defers every `prompt` (so every hook `sendUserMessage`, with or without `deliverAs`) and every
idle `triggerTurn` custom message sent while `agent_settled` is emitted, and runs each one after the event as a run of
its own, depth first; no event a hook sees carries a run id, `agent_settled` carries only `aborted`, and
`pi.sendUserMessage` returns nothing, so a hook can tie a run to a delivery only by the delivery's text (at the user
message's `message_start`, or at `before_agent_start`'s `prompt`). At HEAD the wake hook sets `settled` on every pending
delivery at every `agent_settled` (`hook/wake.ts:1026-1028`), so a wake deferred behind another one counts as
unconfirmed, is sent again, and a second such count blocks its claim: A-089 as the diagnosis says, and the diagnosis's
line numbers for the hook still hold (the wake files are unchanged since `8de6fd7`). The diagnosis's "Related" case
happens too: two `sendUserMessage` calls in one synchronous sweep while the session is idle both pass Pi's `isStreaming`
check before the first one's `_startRun` marks the session busy; the second run's `agent.prompt` throws "Agent is
already processing a prompt", its `finally` emits `agent_settled` inside the first run and clears Pi's busy flag, and its
message is dropped; with the hook as it is, both wakes end blocked and only the first reaches the model. R-038's fake
reproduces the deferral but not that gap (it reserves the session at the send). A deterministic test on the fake needs
no fake change: a test extension that awaits in `agent_settled` holds the settle window open, as Pi's runner awaits
every handler, while the hook's timer sweeps send the planted jobs' wakes, so all of them are deferred; at HEAD the
second wake is then counted unconfirmed and woken twice, every time. Recommended: settle by entry (a delivery is settled
only by the `agent_settled` that follows its own `message_start`), at most one wake started per idle sweep with the rest
sent as follow-ups once the starter's run has begun (a sweep from `before_agent_start`), and a backstop that counts a
wake that never entered; no on-disk format changes. Step 4.14 looks for the unconfirmed line in a log it is never
written to and asks for a finish order the code does not keep.

## 1. Pi 1.5.1: the settle deferral, and what a hook can observe of a run

Paths below are under `adrian-rebuild/input/vendor/pi-coding-agent/package/dist/core/` unless named otherwise.

message), at `input` (`text`, when Pi processes the send) and in `agent_end.messages`. `agent_settled` identifies no
run; a hook can attribute it only to "the run that started last and has not settled", which holds while runs do not
overlap (they do in the race of section 2).

What a send returns: `ExtensionAPI.sendUserMessage(…): void` (`types.d.ts:1312-1315`); the API object calls
`runtime.sendUserMessage(content, options);` and returns nothing (`extensions/loader.js:315-318`); the runtime is
`sendUserMessage: (content, options) => { this.sendUserMessage(content, options).catch((err) => { runner.emitError({ … event:

(`loader.js:311-314`, `agent-session.js:2861-2869`). The Promise-returning forms belong to `ReplacedSessionContext`
(`types.d.ts:349-358`, `agent-session.js:3724-3729`), not to `pi`, and would resolve only after the whole run
(`prompt` awaits `_startRun`, `:1726`). So the hook learns nothing at the send: not whether it was deferred, queued or
thrown, nor the message object.

## 2. Back-to-back idle sends of one sweep ("Related" in the diagnosis): it happens

The hook's call forms (`hook/wake.ts:419-426`): the first send of a sweep while `session.isIdle()` is
`pi.sendUserMessage(message)`, every later one `pi.sendUserMessage(message, { deliverAs: "followUp" })`. Both go
`sendUserMessage` → `prompt(text, { expandPromptTemplates: false, streamingBehavior: deliverAs, images, source:
"extension" })` (`agent-session.js:2012-2039`).

The trace, from the sources (not run). Two sends A, B in one synchronous stretch (`observeEach`, `hook/wake.ts:777-791`,
calls `claimDelivery` → `send()` for every due job with no `await` between them), the session idle and no settle being
emitted:
1. A: `prompt` passes the deferral check (`:1696`), skips commands (`expandPromptTemplates` false, `:1704`), passes the
   compaction check (`:1712`), increments `_promptPreflightCount` (`:1717`; read only by `navigateTree`, `:3364`, not by
   `isStreaming` or `isIdle`) and awaits `_preparePrompt` (`:1720`), which awaits `_runInputHandlers` (`:1736`). With no
   `input` handler that returns at once (`:1655-1657`), so A's continuation is one microtask away. B does the same and
   is queued right behind it.
2. A's continuation reads `this.isStreaming` (`:1749`), which is `this._isAgentRunActive` (`:1127-1129`): false. It
   validates the model and auth (`:1763-1767`; `hasConfiguredAuth` is a synchronous set lookup,
   `model-runtime.js:366-368`) and returns the trigger; `prompt`'s `await this._startRun(…)` (`:1726`) is one more
   microtask away.
3. B's continuation runs first and reads `isStreaming`: still false, because A's `_startRun` (`:1488`) has not run. So
   B's `deliverAs: "followUp"` is never read (`streamingBehavior` matters only inside `if (this.isStreaming)`,
   `:1749-1760`), and B returns a trigger too. Without an option B goes the same way (the throw at `:1750-1752` needs
   `isStreaming`).
4. Both `_startRun`s run (`:1487-1537`); both emit `before_agent_start` (`:1552`). Whichever reaches
   `this.agent.prompt(messages)` (`:1513`) first sets `activeRun` synchronously (`pi-agent-core/package/dist/agent.js:345-354`);
   the other's `agent.prompt` throws `"Agent is already processing a prompt. Use steer() or followUp() to queue messages,
   or wait for completion."` (`agent.js:246-248`) before any `message_start`.
5. The loser's `finally` runs `_emitAgentSettled` (`agent-session.js:1528-1536`): `_isAgentRunActive = false` (`:740`)
   while the winner's run goes on, and `agent_settled { aborted: false }` reaches every extension inside the winner's
   run. Then the error leaves `_startRun` and `prompt` and goes to `runner.emitError` (`:2870-2877`). The loser's text
   was never appended to the agent's messages or the session file (persistence is at `message_end`, `:812-827`).

Verdict: happens, for the hook's two call forms alike. It is deterministic when no extension of the session has an
`input` handler and the provider's auth is a configured one (steps 1–3 then use only microtasks, and B's check precedes
A's `_startRun`); with an `input` handler or an auth check that awaits I/O the order depends on I/O timing, and B is
then either a racing run (the same outcome), a queued follow-up (with `followUp`), or thrown "Agent is already
processing. Specify streamingBehavior…" (without an option). What happens to the second message: dropped, with Pi's
error only on the extension error channel. What the hook sees: `before_agent_start` (prompt A), `before_agent_start`
(prompt B), the winner's `agent_start`, `turn_start`, `message_start` … and one `agent_settled` inside the winner's
run, before or after the winner's user `message_start`. Can an `agent_settled` fire inside another run: yes, here, and
afterwards `ctx.isIdle()` reads true for the rest of the winner's run (`:740`, `:2912`), so every further send in that
run (a timer sweep's wake, the owner's prompt) races the same way.

With the hook at HEAD (derived): at the loser's settle the hook sets `settled` on A and B (`hook/wake.ts:1026-1028`);
neither is entered and answered, so both are counted unconfirmed, attempt 1/2, and their claims removed
(`src/job/wake-delivery.ts:174-210`); the handler's sweep sends both again inside that settle (the hook reads idle),
so Pi defers them; the first re-send's run reads `isStreaming` false, its `agent.prompt` throws again (the winner still
runs), and its own `agent_settled` counts both again, 2/2, blocking both claims with two "… wake was unconfirmed twice;
automatic delivery stopped" toasts (`hook/wake.ts:483-489`); that throw stops Pi's deferred loop (`:750-757`), so the
second re-send never runs. The winner's text reaches the model; no pending delivery is left to match it. Where the hook
makes two idle sends in one sweep today: two due wakes seen by one timer or watch sweep while the coordinator idles
(jobs ending within the 0.5 s timer or the 1 s event debounce, `hook/wake.ts:67-69`, `:835-849`), a start notice and a
completion together, and `/limen on` with two or more held wakes (F042, `hook/wake.ts:1076-1088`). R-050 adds one more:
at `session_start` "delivers undelivered wakes of finished jobs, oldest first" (gate 2 A-033,
`adrian-rebuild/input/gate-2-decisions.md:203`).

R-051 (stage 5, planned) replaces the wakes' `sendUserMessage` with `pi.sendMessage(…, { deliverAs: "followUp",
triggerTurn: true })` (gate 2 A-034 revision 4, `gate-2-decisions.md:204`): `sendCustomMessage` calls `_startRun`
synchronously when idle (`agent-session.js:1972`, `:1488`), so this race does not exist for custom messages; the settle
deferral does (`:1968-1970`).

## 6. Design options for "a delivery is settled only by the settle of the run it entered"

1. Settle by entry. The `agent_settled` handler sets `settled` only on the deliveries in `activeDeliveries` (those whose
   `message_start` came since the last settle), not on every pending one (`hook/wake.ts:1026-1028`); `confirmDeliveries`
   keeps its rules. A deferred delivery stays pending with its claim and fresh `live`, so no other run's settle counts it
   and no sweep re-sends it (`wake-delivery.ts:74-76`); the deferred order then reorders only distinct wakes, each matched
   by its own text. Gap: a delivery Pi drops (section 2's loser, a deferred action after a throwing one, a follow-up
   sent during a manual `/compact`, which `prompt` throws at `agent-session.js:1712-1714`, a queue the TUI clears,
   `modes/interactive/interactive-mode.js:3992`) never enters and would stay pending until the session ends, where today
   the next settle of any run counts it. So it needs a backstop: a delivery accepted, not entered, with the session read
   idle at a sweep and no run started since it was sent for at least a threshold (`CLAIM_STALE_MS`, 30 s), is counted
   unconfirmed through `recordUnconfirmed` (same count and block). Moving parts: one loop changed, one `sentAt` field,
   one check in the sweep. Disk: none. Section 2's race: not handled (its spurious settle can settle an entered,
   unanswered delivery, and its loser waits for the backstop).
2. Sends out of the settle window. The settle handler no longer sweeps inside the event (it schedules the sweep for
   after the event, or leaves it to the timer), and an idle sweep sends at most one wake; "every pending delivery settles
   at the next settle" stays. Moving parts: two small edits. Disk: none. It handles the hook's own settle-handler sends
   and section 2's race for the hook's own sends, but the guarantee rests on timing: a window held open by another
   extension's awaiting `agent_settled` handler (`extensions/runner.js:821-848`) still catches timer sweeps, and then the
   A-089 chain returns unchanged, re-sends entering before first sends (the test of section 5 holds the window exactly
   so, and fails under this option). z. 14 ("Gwarancje w kodzie, nie w prompcie") favours a rule in code.
3. Settle by entry, one starter per idle sweep (recommended). Option 1 with its backstop, plus: (a) once a sweep has
   sent a wake while idle, it sends nothing more (the remaining `send()`s return `false`, which releases the claim with
   no attempt, `wake-delivery.ts:106-111`; the toast in `sendCompletion`/`sendAdvisory`, `hook/wake.ts:529-539`,
   `:619-624`, moves after that check so a skipped wake does not toast); (b) a `before_agent_start` handler in the hook
   calls `sweep()`, and a sweep requested while one is in flight runs once more in `finishSweep`'s `finally`
   (`:828-833`), so the remaining wakes go as follow-ups into the starter's run (Pi has set `_isAgentRunActive` before
   `before_agent_start`, `agent-session.js:1488`, `:1552`; the fake's `startRun` before `prepare`). Deferred order: as
   option 1; at most one hook send per sweep is ever deferred. Section 2: the hook never makes two idle sends that can
   race; races with the owner's prompt in the same microtask gap remain (rare). Batching stays: several wakes enter one
   turn, so `test/s3-finish-wake.test.ts:199-200` stays true, deterministically. Disk: none. It survives R-051: with
   custom messages (a) is harmless and settle by entry is still needed (`agent-session.js:1968-1970`); R-051's matcher
   must then accept `role: "custom"` (`hook/wake.ts:979-981` returns for any role but `user`).
4. Run binding by `before_agent_start`. Bind a delivery to the run whose `before_agent_start` `prompt` equals its text
   (a starter) or to the run active at its send (a follow-up); settle a run's deliveries at the settle after its start;
   count a starter whose run settled with no `agent_start` (section 2's loser). More state, and it still cannot pair
   settles with runs when two runs overlap, so it needs (a) of option 3 anyway. Not recommended over 3.
5. One message for every wake of an idle sweep. Changes the wake's form and the matcher's text equality (`:986-988`);
   R-051 changes the form anyway. Rejected.

Recommendation: option 3. Reliability first: A-089 is fixed by a rule in code that holds whatever other extensions do
in `agent_settled`, section 2's race is not produced by the hook's own sends, and a wake that never enters is counted
instead of waiting silently (T-01; at-least-once is the documented failure direction, `docs/remote.md:86`).
Determinism: both new tests fail before every time and pass after; no timing assumption in the guarantee. Autonomy: no
"automatic delivery stopped" that waits for Adrian. Cost: wakes due together still enter one coordinator turn (one
request of about 300k cache-read tokens each, M-03). Four small moving parts in `hook/wake.ts`, none in
`src/job/wake-delivery.ts`.
