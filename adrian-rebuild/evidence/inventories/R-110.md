## 3. What Pi 1.5.1 allows

- Every `before_agent_start` handler may return one `message`; Pi collects one per handler, in load order
  (pi:`core/extensions/runner.js:1137-1153`; result type pi:`core/extensions/types.d.ts:1145-1149`). So a hook gets a
  second message into a run by registering a second handler.
- A run's messages, in order: the prompt (or the triggering custom message), pending `nextTurn` messages, then the
  handlers' messages (pi:`core/agent-session.js:1560-1587`). The session is busy from `_startRun`'s first line, so
  "messages sent while before_agent_start handlers run are queued into this run" (`:1481-1488`); one sent with
  `triggerTurn: false` then is flushed **before** the starting messages (`:1501-1504`); one sent with
  `followUp`/`triggerTurn: true` goes to `agent.followUp` and enters only when the agent would stop, one more request
  (`:1959-1966`; E-16). A message returned by the handler lands after the prompt with no extra request.
- `sendCustomMessage` dispatch (`:1946-1984`): `nextTurn` → pending; streaming and `triggerTurn !== false` → steer or
  followUp; idle with `triggerTurn` → a new run; streaming with `triggerTurn: false` → held to the turn's end; idle with
  no trigger → appended at once (`:1985-1990`).
- Run messages of role `custom` are persisted as `CustomMessageEntry` with `customType`, `content`, `display` and
  `details` (`:814-820`); `CustomMessageEntry` is `{ type: "custom_message"; customType; content; details?; display }`
  (pi:`core/session-manager.d.ts:109-115`); `details` is "extension-specific metadata (not sent to LLM)" (`:101-102`)
  and the model gets only `content` (pi:`core/messages.js:89-96`). This settles R-039 inventory Unverified 5.
- The handler context's `sessionManager` (pi:`core/extensions/runner.js:642-645`) is a `ReadonlySessionManager` with
  `buildContextEntries` (pi:`core/session-manager.d.ts:178`, `:319-323`), whose implementation keeps the compaction
  entry, the kept range and everything after it (pi:`core/session-manager.js:201-229`). A hook can therefore find, at
  the start of every run, the last digest and every notice still in the model's context, and the frozen
  `limen-context` bytes (R-039's rule).
- Nothing in Pi watches files for an extension; a watcher would be the hook's own `fs.watch`.

## 4. What reaches the model under the bridge

- A custom message (cue, digest, notice) reaches the model as `user` (E-1, E-11; pi:`core/messages.js:89-96`).
- On REUSE "only the new trailing run of Pi user messages is sent as the prompt" (bridge:`27`), joined with `"\n\n"`
  (bridge:`38`, `:396`): a coordinator run's request ends with `<prompt>\n\n<cue>\n\n<notice>\n\n<digest>` when the
  handlers return them in that order. On REBUILD (a first turn with history, a compaction, an abort; bridge:`28`)
  "Each Pi user or custom message is its own record" (bridge:`400`). A continuation's first query is a first turn
  with history, so REBUILD: the parent's context message is a record of the rewritten session and the child's task,
  cue and notice are the prompt (bridge:`316`; derived from the evidence file, not run).
- "A `context`-event injection is not a substitute … On REUSE only the trailing user run is sent" (bridge:`342`): the
  digest must be a session entry of the run, not a `context` rewrite.
- A message sent mid-run as steer or follow-up is "held until the Claude Code turn ends, then sent as a continuation
  `query()`" (bridge:`39`): delivering the digest right after a land's tool result would cost a query of its own.
- How R-038's fake proves it: each model call's `messages` in `fake-view.jsonl` with roles and the `reuse`/`rebuild`
  path (R-038 `ticket.md:138-150`), so a test reads the last user message of a call and checks that it ends with the
  digest only after a change, that the context message is present once with the same bytes, and that a continuation's
