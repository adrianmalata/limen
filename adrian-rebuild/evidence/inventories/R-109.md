## 2. How a directive is rendered

- The unit model and the one renderer are in `src/platform/systemd-units.ts`. `seat/units.ts` imports `renderUnit`
  from it (`seat/units.ts:7`; header `:1-6`; renderer header `systemd-units.ts:1-9`).
- `directiveLine` (`systemd-units.ts:123-129`) writes `Key=value` as given. It refuses a key that does not match
  `/^[A-Z][A-Za-z]*$/` (`:43`), an empty value, and a value with a control character. It quotes and escapes nothing.
- The one escaping in the module is the sweep's `PATH`: `pathAssignment` (`systemd-units.ts:99-108`) returns
  `"PATH=…"`, quoted whole, with `\`, `"` and `%` escaped. The reasons: "systemd splits an unquoted value at white
  space, with each backslash and quote escaped as inside quotes and `%` doubled, since systemd reads specifiers there".
  It is used once (`:73`) and tested at `test/platform/systemd-units.test.ts:36-52` (line 47) and `:93-99`.
- `NODE_OPTIONS=--dns-result-order=ipv4first` holds no white space, quote, backslash or `%`. So the unquoted
  `Environment=NODE_OPTIONS=--dns-result-order=ipv4first` reads as one assignment (Q1). It is 53 characters long, under
  the 100-character limit of T-10 (`test/seat/units.test.ts:62-68`).

## 9. Open design questions

Q1, technical (category A of D-054 (2)): how the line is written.
- (a) `["Environment", "NODE_OPTIONS=--dns-result-order=ipv4first"]`, unquoted, from a named constant in
  `seat/units.ts` with a comment that cites D-108.
- (b) Quoted through an escaping function exported from `systemd-units.ts` (a general form of `pathAssignment`).
- (c) A typed `environment` field on `UnitDefinition`, rendered by the renderer.
- Recommendation: (a). The value holds none of the characters the quoting exists for (`systemd-units.ts:99-105`).
  T-25 (2) (`taste.md:1222-1223`): "Code without a policy (a pure function with no I/O and no error handling) may stay
  local; when a second module needs it, it moves to the module that owns the concept". `seat/units.ts` does not need
  the function, and (b) and (c) are more than an S ticket needs.

Q2, technical (category A): where the line goes and how the test names it.
- (a) After `ExecStart=` in `[Service]`. The golden test (`test/seat/units.test.ts:16-39`) gains the line, with a
  `// D-108:` comment above the test, and its name may add "with IPv4 first".
- (b) Leave the golden test as it is except for the line, and add a separate test "D-108: limen-alerts.service has
  Node try the relay's IPv4 address first".
- Recommendation: (a). The golden text must change either way. T-29 (3) asks for one mechanism per test, and the
  rendered text is that one mechanism. A second test would assert the same line twice.

Q3, technical (category A): the doc sentence.
- (a) One sentence in `docs/seat/README.md:29` (for example: the service sets
  `NODE_OPTIONS=--dns-result-order=ipv4first`, since the relay refuses the seat's IPv6 sender for its daily quota),
  naming no address.
- (b) No doc change.
- Recommendation: (a). That paragraph lists the service's settings, and an operator who reads the unit should find
  the reason for the new line.

Q4, plan question for Adrian (a wording fix of `## Deployment` 4.11, not of the ticket's change): what 4.11 asks.
- (a) Keep "the alerts' install again as in 3.3".
- (b) Drop the install, since 4.0's deploy already wrote the unit (section 8). Remove the drop-in, `daemon-reload`, then
  check that `systemctl show -p Environment limen-alerts.service` names the setting, and keep the 429 and phone checks.
- Recommendation: (b). The install is a no-op after 4.0. The `show` check proves that the unit, not the drop-in, now
  carries the setting, which is D-108's condition for removing the drop-in ("once a tag with it is deployed").
