## 1. The rule today

- `NOT_ACTIVE = 3` (`src/platform/linux.ts:51-52`). Its comment: "The exit status of `systemctl is-active` for a unit
  that is not active (LSB "program is not running")".
- `ENDED_STATES = {inactive, failed}` (`linux.ts:53-57`): "It exits 3 for every state but `active` and `reloading`, a
  `deactivating` scope included, which may still hold processes, so the printed word decides."
- `scopeState(unit, cgroup)` (`linux.ts:232-249`):
  1. a known cgroup whose folder is missing → `gone`, with no call (`:240-242`);
  2. `systemctl --user is-active <unit>` (`:243`);
  3. exit 3 → `gone` if the word is `inactive` or `failed`, else `active` (`:244-246`);
  4. any other exit → `callFailure` (`:247-248`): exit 0 → `active`; anything else → `failed` with a detail.
- `callFailure` (`linux.ts:327-336`): the spawn error, else the first stderr line, else `ended by <signal>`, else
  `exit code <n>`. With `inactive` on stdout and nothing on stderr, exit 4 gives the detail `exit code 4`.
- The doc comment calls this "the one place of that rule; the end of a scope reads it here too" (`linux.ts:237-238`).
  `endScope` reads it first (`linux.ts:261-267`).
- A "record with no cgroup" is a record with no `scope` at all: inside `Scope` the cgroup is required
  (`src/job/record.ts:149-152`), and every caller passes `record.scope?.cgroup`. The wrapper writes the scope in the
  transition to running (`record.ts:145-147`). So the affected jobs are those that ended before their wrapper ran.

## 3. Where exit 4 reaches today

Path 1, the end of a job (the case seen on the seat). `finalizeJob` always ends the scope after the terminal record
(`src/job/finalize.ts:151-157`). `endJobScope` (`finalize.ts:185-194`) calls `endScope(jobScope(id), undefined)` for a
record with no scope. Its comment says "a scope that never started is gone, with nothing to log" (`finalize.ts:180-183`).
On systemd 259 the unit never existed, so `is-active` exits 4 and the end:

- appends `scope <unit> was not ended: exit code 4` to the job's log (`finalize.ts:190`);
- calls `onScopeNotEnded`, which only the wrapper passes: a SIGKILL to its own process group
  (`src/runtime/wrapper.ts:219`).

Path 2, the sweep's leftover scopes (the `stuck` path). `endLeftoverScopes` (`reap.ts:265-301`) reads each terminal
record whose unit is in the sweep's live listing or that already has `stuck` (`:271-274`). Then:

1. `scopeState(unit, undefined)` returns `failed`, not `gone` (`:276`);
2. with the wrapper not alive and the recovery claim taken (`:282-288`), `terminateScope` (`:310-344`) returns `not
   ended` at once (`found`, `:327`);
3. `notEnded` (`:245-254`) appends `reap: <unit> not ended: exit code 4` to the job's log and adds one to
   `stuck.attempts`;
4. the record now has `stuck`, so every later run repeats steps 1-3 (`:272`), and `is-active` keeps exiting 4;
5. from 3 attempts, `escalatedStuck` returns it (`STUCK_ESCALATION = 3`, `src/job/record.ts:843-852`). The alerts
   send `stuck` (`seat/alerts.ts:111-116`), and `limen status` lists the job (`src/project/summary.ts:240-248`).

The plan marks this path "from the code, not seen" (`plan.md:2198-2199`, `:5011-5012`).

Path 3, a record with a scope. The folder test comes first (`linux.ts:240-242`), so a collected scope is `gone` with no
call. `is-active` runs only while the folder exists. If systemd collects the scope between the `stat` and the call, one
read can be `failed` with `exit code 4`, and the next read finds no folder. This race is an inference from the code;
nothing was observed.

Where the lines go. `appendLimenLog` writes `<jobDir>/log` only (`src/job/record.ts:1183-1186`). The sweep prints only
its own lines (`printed`, `src/runtime/sweeping.ts:150-155`, and the lines at `:183`, `:188`, `:332`). A
`notEnded` is not a thrown failure, so it does not reach the run's final error either (`sweeping.ts:244-256`). Neither
"not ended" line reaches the sweep's journal. Section 8 covers what this means for step 4.13.

## 7. T-01 and T-25: one definition of "not active"

- T-01 (`taste.md:637-641`): "An expected absence (`ENOENT`, a dead process) is an explicit condition, never a
  catch-all." An `inactive` from a manager that does not hold the unit is that kind of absence. Every other exit stays a
  failure through `callFailure`, and `linux.test.ts:235-242` already proves that for exit 1. The condition is explicit
  (named exits and named words), so no failure vanishes. (Whether systemctl also exits 4 for a real call failure is in
  "Unverified".)
- T-25 (1) (`taste.md:1214-1218`): "Code with a guarantee or a policy has exactly one module". The rule "this scope has
  no process left" lives in `scopeState` alone (`linux.ts:237-238`), and every scope reader goes through it
  (`endScope`, `reap.ts`). So the not-active exits should be one named constant in `linux.ts`, used by `scopeState`
  only, in place of `NOT_ACTIVE = 3`. `unitAnswer` answers another question ("is this unit active?", exit 0 only) and
  needs no part of that set. Making it tell "says no" from "could not ask" is R-060's (section 4).
- The comments that say "exits 3" must change with the code: `linux.ts:51`, `:54`, `:234`. T-30 (2): identifiers
  must resolve. An `E-18` in a code comment has precedent (for example `src/runtime/wrapper.ts:350` cites E-17, and
  `hook/rate-limit.ts:8` cites E-9).

## 9. Open design questions

Q1, technical (category A of D-054 (2)): how exit 4 reads.
- (a) Exits 3 and 4 share one rule, and the printed word decides: `inactive`/`failed` → `gone`, any other word →
  `active` (retried at the next sweep).
- (b) Exit 4 is `gone` whatever the word, since systemd uses 4 for a unit it does not hold.
- (c) Exit 4 is `gone` only with `inactive`; exit 3 keeps today's rule.
- Recommendation: (a). The note says "Exits 3 and 4 both read as not active" (`plan.md:2199`). The word rule exists
  because a `deactivating` scope may still hold processes (`linux.ts:53-56`; R-027 review round 1, finding 4, cited at
  `test/platform/linux.test.ts:281`). E-18 says 259 prints `inactive` with exit 4, so (a) is enough for what was seen,
  and it keeps one rule (T-25).

Q2, technical (category A): where the "fake `systemctl` test returns 4" lives.
- (a) Only the one-test fake in `test/platform/linux.test.ts` (section 6, item 1).
- (b) Also the plant's fake answers exit 4 for a scope whose folder is missing (section 6, item 2).
- (c) Only the plant.
- Recommendation: (b). Item 1 is the failing unit test that T-29 (1) places. The plant change is a few lines, and it
  makes the whole suite meet systemd 259's answer. It also turns `test/job/finalize.test.ts:205-214` into a proof of
