## 5. The fake engine today

**Where.** `test/fake-engine.mjs` (300 lines), the one fake `pi`: "It loads the real hook extensions Limen passes, runs
the task text as a script, and records what it saw in the record dir" (`:2-3`). The plant links it as `pi` on the

No file of `src/`, `hook/`, `seat/` or `bin/` names it (`git grep -n -i 'fake' -- src hook seat bin` prints nothing).

**How it loads hooks.** Each `--extension <path>` is imported in argv order and its default export is called with the
fake `api` (`:211-214`). Pi loads them through jiti (E-4, `plan.md:1528`); the fake uses Node's own import, with type
stripping (`package.json:28-29`, Node ≥ 24). A job gets `--no-extensions` plus its `--extension` list
(`src/runtime/engine.ts:96`, `:104-115`); a coordinator loads `.pi/extensions/limen.ts`, which loads `wake`,
`communication`, `steering` and `group-peer` (`.pi/extensions/limen.ts:8-11`).

**Its API** (`:138-155`): `on`, `registerTool`, `registerCommand`, `sendUserMessage`, `sendMessage`, `events`. Its
context (`:112-123`): `cwd`, `ui`, `isIdle`, `shutdown`, `sessionManager.getSessionId/getSessionFile/getSessionName`.

**What it records.**
- `fake-argv.json`, `fake-env.json` (names only), `fake-task.txt` (`:38-41`).
- The transcript line: `appendFileSync(join(flag("--session-dir"), "fake.jsonl"), `${JSON.stringify({ task })}\n`)`
  (`:44`), once per engine process.
- `fake-events.jsonl`: the pid (`:47`), every delivery as `{ event: <deliverAs or kind>, text }` (`:129`), notices,
  rate-limit and SIGTERM events, the exit (`:299`).
- `fake-system.txt`: each `before_agent_start` handler's returned `systemPrompt`, joined (`:218`).
- `fake-context.txt`: each handler's returned `message.content`, joined (`:219`).
- On stdout: `agent_start` (`:220`), the assistant `message_end` cut inside multi-byte letters (`:185-191`), tool
  events (`:240`, `:242`).

**How a run is modelled** (R-096, D-069): `deliver` queues a non-steer message as role `custom` or `user` and chains a
`run` (`:128-137`). `run` sets `idle` false, runs a turn, then one turn per batch queued meanwhile, then sets `idle`
true and fires `agent_settled` once (`:156-169`). `turn` fires `message_start`/`message_end` per message,
`turn_start`, `context` with that turn's messages only, the assistant reply, `message_end`, `turn_end` (`:170-194`).
The task's own run is chained last, and the script awaits it (`:294-297`), then fires `session_shutdown` and exits
(`:298-300`).

**What no test can see today.**
- The text the model receives, in order. The task (`fake-task.txt`), the cue (`fake-context.txt`), the deliveries
  (`fake-events.jsonl`) and Pi's system prompt (`fake-system.txt`) sit in four files, and none applies the bridge's
  mapping.
- The system prompt: the fake records what the hooks return (`:218`), which the bridge drops (E-1). This is A-086's
  blind spot (`audit.md:1705`).
- The cue in the run: the fake records the `before_agent_start` message (`:219`) but never puts it into a turn; Pi
  adds it to the run after the prompt (`agent-session.js:1578-1589`).
- Later runs: `before_agent_start` fires once per process (`:217`, the only call); Pi fires it once per run (E-11).
- Steers: `deliver` returns on `steer` before queueing (`:130-132`), so a steer never enters a turn; Pi's `agent.steer`
  enters the next request (`bridge-5.0.3.md:371`).
- `triggerTurn` and `nextTurn`: `sendMessage` passes only `deliverAs` (`:143`), so every message starts or joins a run.
  Pi appends a `triggerTurn: false` message without a run when idle and holds it until the turn ends while busy
  (`agent-session.js:1974-1983`); `nextTurn` waits for the next run (`:1956-1957`).
- Tool results: the `tool` word fires only `tool_execution_start` and `tool_execution_end` (`:240-243`). R-017 noted:
  "it fires no `tool_call`, `tool_result` or `agent_before_settle`" (`R-017-pi-api-adapter/outcome.md:276-278`). So the
  communication hook's reminder in a tool result (`hook/communication.ts:110-134`) never shows.
- The full context: Pi's `context` event holds every message except `system` ones (`dist/core/extensions/runner.js:
  1014-1022`); the fake passes only the turn's messages (`:177`).
- Compaction and `agent_end`: the fake fires neither `session_compact` nor `agent_end`; the adapter declares
  `session_compact` but not `agent_end` (`src/runtime/pi-api.ts:70`).

**The `agent_settled` case.** In `run`, `idle` is true before `agent_settled` fires (`:167-168`). A hook that sends
during that event sees an idle session; `hook/wake.ts:421-423` then calls `sendUserMessage(message)`, which reaches

## 7. `limen stats` and the `{"task": …}` line

- The one reader of Pi session files is `src/job/usage.ts` (`:1-9`). `readSessionFile` parses each line with
  `parseJson(…, entryOf)`; a line that fails becomes a `BadData` in `unread` (`:112-123`).
- `entryOf` first reads `string(fields.get("type"), at(field, "type"))` (`:202-203`). `string` throws a mismatch for
  a value that is not a string (`src/boundary.ts:222-224`). `{"task": …}` has no `type`, so it is unread.
- A Pi header (`type: "session"`) and any entry type with no `usage` other than `custom_message` give `undefined`, no
  error (`:207-209`). A `custom_message` or a `message` needs an ISO `timestamp` (`:255-257`); an assistant message
  needs `provider`, `model` and four integer usage classes (`:218-237`, `:260-269`). Pi's shapes:
  `session-manager.d.ts:5-12` (header), `:23-26` (message entry), `:109-115` (custom message entry).
- `limen stats`: `readJob` → `readSessionUsage` (`src/job/statistics.ts:206-212`); a job with unread lines is counted
  in `skipped.transcripts` (`:194-195`) and printed as "`<n> transcript line(s) of <id>`" on the `Not read:` line
  (`:643-661`, `:651`). `limen show` reads only the usage (`src/job/listing.ts:117`), so it prints nothing about it
  (R-024 Open point 1).
- No test runs `stats` or `show` over a fake job: `git grep -n 'spawnJob\|waitJob\|"spawn"' --
  test/job/statistics.test.ts test/cli/stats.test.ts test/cli/show.test.ts` prints nothing. The stats tests plant
  their own Pi-shaped lines (`test/cli/stats.test.ts:68`, `:398`, `:419`).
- Other readers of the session folder: `limen continue` needs at least one `*.jsonl` (`JOB_NO_SESSION`,
  `src/job/continuation.ts:468-472`) and copies the newest one (`:569`, `src/job/publication.ts:116-120`); the
  session-commands reader keeps lines with `"toolCall"` or `"toolResult"` (`src/job/session-commands.ts:112-126`); the

- Constraints on a new transcript shape from the tests: the parent "holds one transcript" (`test/cli/continue.test.ts:
